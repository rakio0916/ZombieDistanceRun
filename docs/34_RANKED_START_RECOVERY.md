# ランキング開始で前の走行が残った場合の復旧

2026-09-22の報告では、通常ブラウザーで「ランキングに挑戦」が始まらず、再読み込みでも解消しなかった。本番Workerでは11:03:16 JSTの認証済み`POST /api/v1/runs/start`が200で走行を発行した後、11:04台の再開始11回が409になった。本番D1には同じ開始時刻の初級v7 runが`RUNNING`で残り、finishがない。最初の200応答後に画面が進まなかった原因は未観測である。

## 変更

- `ACTIVE_RUN_EXISTS`の409応答に、その認証利用者の`active_run_id`を含める。別利用者のrunは返さない。
- 選択画面の開始ボタン直下に原因を表示し、別タブの走行を続けるか、前の走行を破棄して再挑戦するかを利用者に選ばせる。破棄は明示的な操作のみで、ランキングへ登録しない。
- `POST /api/v1/runs/{run_id}/abandon`を追加する。既存の`ranked-run-abandon`契約の`schema_version=1.0.0`、`reason=USER_EXIT`、`at_tick=0`を再読み込み後の復旧に用いる。前ページのtickは回収できないため0とし、この値で距離や順位を生成しない。
- serverは認証主体とrun所有者を照合し、`RUNNING`だけを条件付きで`REJECTED`へ更新する。既に`REJECTED`なら冪等成功、`VERIFIED`などは409。前の走行が別タブで完了していた場合は再開始のみを試す。
- 開始通信と破棄通信を10秒で打ち切り、結果不明ならエラーを表示する。応答を失った開始がserverで成功していた場合、次の開始時に409と回復操作へ進める。通信失敗を理由に練習へ自動移行しない。

## 検証と境界

- 所有者以外を破棄できないこと、確定記録を上書きしないこと、同じ破棄の再送が安全であることをSQLiteテストで確認した。39 test、lint、TypeScript型検査、buildを通過。ローカルWorkerの新abandon routeは未ログインを401で拒否し、選択画面はHTTP 200を確認した。
- Core／ruleset／model／既存のfinish・ranking判定、公開範囲、D1 schemaは変更しない。
- 実iPhone／Androidでの画面操作と、実認証での`start → 409 → abandon → start → finish`は別途確認する。最初の200成功後に画面が進まなかった原因の特定にも同じ環境での再現が必要。
